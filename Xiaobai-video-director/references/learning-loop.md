# 反馈回灌与回归流程 v2

用户指出画面问题后，先修最早的根因，不在某条视频的 React 里继续堆补丁。

1. 在 run 的 `feedback.json` 记录版本、时间段、实际现象、用户原意和问题发生阶段。
2. 区分内容理解、对象/关系建模、机制状态、cue、几何/层级、镜头、声音、验收；找到实际执行代码。模型正确但组件另抄数据时，应关闭平行执行入口。
3. 能机械检查的根因更新 `score.py` 或共享 `ScoreStage.tsx`，在 `check_score.py` 留一个本来会放过、现在必须失败的输入；兼容旧路径时运行 `check.py`。不能用新增条款替代失败用例。
   当前 `score-render` 会先运行 `check_score_render.py`，从实际共享 JSX 生成 SVG，阻断浮点尾数和水平装饰线穿字的已知回归；无需联网、配音或完整重渲染。它只检查这两个已复现缺陷，复杂遮挡及动作是否多余仍需实片复核，不能将此项通过当作全片观感通过。
4. 抽象同类经验，增强已有核心/Profile 稳定 id；具体坐标和截图留在 run。新经验必须接入 `compile_file` 支持清单和复核项，否则自动阻断，不静默忽略。旧规则内容变更也会改变编译凭据，需要重渲染。
5. 用新版本路径生成候选，重新抽取动作前、中、落定的真实帧。审查文件默认 pending；按每句和每条经验检查实际画面、连续运动及声音。缺项、不通过、模型或视频过期均不能 `score-release`。

真实帧绑定能防止拿旧视频或无关截图验收；它不能证明复核者诚实，也不能用像素占比推导“观众一定懂”。不要自动批量填 pass 或伪造播放记录。不能实际听看时明确保持待复核。

旧参数示例仅用于历史诊断；新产物唯一流程是 `score.json → score-check → score-render → score-review → score-release`。最多两轮定向修复，仍不合格就保留候选与证据并指出缺口。新机制先短片验证，不能把一条样片成功等同于跨材料稳定。
